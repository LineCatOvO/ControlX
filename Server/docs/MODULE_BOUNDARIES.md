## 概述

本文档定义了ControlX输入系统的模块边界，明确各模块的职责、权限和交互方式。模块边界的设计遵循以下原则：

- **单一职责**：每个模块只负责一个核心功能
- **明确边界**：模块之间有清晰的职责划分
- **最小依赖**：模块之间依赖关系最小化
- **权限控制**：关键操作需要权限验证

---

## 核心模块职责

### 1. ApplyScheduler（应用调度器）

**职责**：输入系统的【唯一时间权威】，负责固定频率（125Hz）的状态应用调度。

| 功能 | 说明 |
|------|------|
| 时间权威 | 生成和分发统一的tickTime |
| 状态调度 | 以固定频率应用最新状态到执行器 |
| 时间同步 | 将tickTime同步给其他模块 |
| 模式支持 | 支持普通模式、影子模式、Router-only模式 |

**允许操作**：
- ✅ 生成tickTime
- ✅ 调度状态应用
- ✅ 同步时间到其他模块

**禁止操作**：
- ❌ 状态验证（由Validator负责）
- ❌ 直接操作执行器（通过ExecutorManager）
- ❌ 安全清零（由SafetyController负责）

---

### 2. SafetyController（安全控制器）

**职责**：输入系统的安全守护者，负责在异常情况下立即清零所有输入状态。是【唯一允许触发清零】的模块。

| 功能 | 说明 |
|------|------|
| 清零权限控制 | 通过权限令牌机制控制清零权限 |
| 超时检测 | 检测状态接收超时，自动触发清零 |
| 异常处理 | 处理WebSocket断连、状态异常等 |
| 清零记录 | 记录所有清零操作的原因、时间、权限类型 |

**允许操作**：
- ✅ 触发清零
- ✅ 管理权限令牌
- ✅ 记录清零历史
- ✅ 检测超时

**禁止操作**：
- ❌ 验证状态合法性（由Validator负责）
- ❌ 存储状态（由StateStore负责）
- ❌ 生成时间戳（由ApplyScheduler负责）

---

### 3. Executor（输入执行器）

**职责**：输入系统的执行层核心，负责管理所有输入执行器的生命周期和状态应用。

| 功能 | 说明 |
|------|------|
| 执行器管理 | 创建、配置和管理所有输入执行器 |
| 状态应用 | 将输入状态应用到实际硬件或模拟设备 |
| 模式切换 | 支持生产模式、测试模式、DryRun模式 |
| 安全控制 | 集成SafetyController，确保异常情况下的安全清零 |

**允许操作**：
- ✅ 管理执行器生命周期
- ✅ 应用输入状态
- ✅ 触发安全清零

**禁止操作**：
- ❌ 状态验证（由Validator负责）
- ❌ 状态存储（由StateStore负责）
- ❌ 时间管理（由ApplyScheduler负责）

---

### 4. Validator（输入验证器）

**职责**：输入系统的质量把关者，负责验证输入状态的合法性、完整性和一致性。

| 功能 | 说明 |
|------|------|
| 状态验证 | 验证键盘、鼠标、摇杆、手柄状态的合法性 |
| 范围检查 | 验证数值范围（摇杆值[-1,1]、扳机值[0,1]等） |
| 序列号验证 | 验证frameId的单调递增性 |
| 错误报告 | 提供详细的验证错误和警告信息 |

**允许操作**：
- ✅ 验证状态合法性
- ✅ 报告验证错误
- ✅ 提供验证结果

**禁止操作**：
- ❌ 修改输入状态
- ❌ 触发安全清零
- ❌ 直接操作执行器

---

### 5. StateStore（状态存储）

**职责**：输入系统的状态管理中心，负责管理输入状态的存储、历史记录和序列号校验。

| 功能 | 说明 |
|------|------|
| 状态存储 | 存储最新的输入状态和历史状态记录 |
| 序列号管理 | 验证和管理状态序列号的单调性 |
| 时间记录 | 记录状态接收时间和应用时间 |
| 状态标准化 | 将数组类型转换为Set类型，补充默认值 |

**允许操作**：
- ✅ 存储状态
- ✅ 管理历史记录
- ✅ 验证序列号
- ✅ 标准化状态

**禁止操作**：
- ❌ 验证状态合法性（由Validator负责）
- ❌ 应用状态（由Executor负责）
- ❌ 触发清零（由SafetyController负责）

## 时间权威性说明

### 核心原则

ApplyScheduler是整个输入系统的【唯一时间权威】，所有时间相关操作都必须使用ApplyScheduler提供的tickTime。

### 时间流向

```
ApplyScheduler.tickTime
       │
       ├──► SafetyController.currentTickTime
       │
       ├──► StateStore.recordAppliedState(tickTime)
       │
       └──► SafetyController.recordValidState(tickTime)
```

### 禁止行为

| 模块 | 禁止操作 | 正确做法 |
|------|----------|----------|
| SafetyController | 禁止调用Date.now()进行超时判断 | 使用currentTickTime |
| StateStore | 禁止自行记录时间戳 | 使用ApplyScheduler提供的tickTime |
| Executor | 禁止自行获取时间戳 | 使用ApplyScheduler提供的tickTime |

## 清零权限机制

### 权限类型

| 类型 | 说明 | 使用场景 |
|------|------|----------|
| `internal` | 内部清零 | SafetyController自身触发（超时、断连等） |
| `external` | 外部清零 | 持有有效令牌的外部模块触发 |
| `emergency` | 紧急清零 | 无需令牌，用于真正的紧急情况 |

### 权限令牌机制

```typescript
// 1. SafetyController创建令牌
const token = safetyController.createPermissionToken('module-id', 'external');

// 2. 外部模块使用令牌请求清零
const success = safetyController.requestClear('reason', token.getId());

// 3. SafetyController验证令牌并执行清零
// 4. 记录清零操作（包含tokenId）
```

### 清零记录

每次清零操作都会记录以下信息：

```typescript
interface ClearRecord {
    timestamp: number;      // 清零时间戳
    reason: string;         // 清零原因
    permission: ClearPermission;  // 权限类型
    tokenId?: string;       // 令牌ID（可选）
}
```

## 最佳实践

### 1. 时间一致性

- ✅ 始终使用ApplyScheduler提供的tickTime
- ❌ 禁止在各模块中调用Date.now()

### 2. 清零操作

- ✅ 通过SafetyController触发清零
- ❌ 禁止直接操作执行器进行清零

### 3. 状态验证

- ✅ 在存储前验证状态
- ❌ 禁止在验证器中修改状态

### 4. 模块通信

- ✅ 通过明确的接口进行模块间通信
- ❌ 禁止跨模块直接访问内部状态

### 5. 错误处理

- ✅ 异常情况下触发SafetyController清零
- ❌ 禁止在异常情况下继续操作执行器
