## 2. 系统总体架构

### 2.1 系统概述

ControlX 是一个远程赛车输入控制系统，允许通过安卓设备上的用户操作生成控制结果，使目标赛车游戏在无需修改的情况下响应这些控制。

系统的核心目标：

> **在安卓设备上，通过用户操作生成控制结果，使目标赛车游戏在无需修改的情况下响应这些控制。**

系统应保证控制行为稳定、可预测，并在异常情况下不会产生残留输入。

```
     ↓

     ↓
Windows 游戏响应
```

## 3. 模块划分与职责边界

### 3.1 系统分层

系统分为两大子系统：

| 子系统 | 平台 | 主要职责 |
|--------|------|----------|
| Android Client | Android | 输入采集、布局执行、控制状态生成、通信 |
| Node.js Server | Windows | 接收校验、状态调度、输入映射、虚拟设备 |

### 3.2 Android Client 模块划分

| 模块 | 职责 | 输入 | 输出 |
|------|------|------|------|
| Input Layer | 原始输入采集（触控、陀螺仪） | MotionEvent | 归一化输入值 |
| Layout Engine | 三层布局执行 | 归一化输入值 | ControlResultState |
| Transport Layer | WebSocket 通信 | ControlResultState | ACK、RTT |

#### Layout Engine 三层结构

| 层级 | 职责 | 特性 |
|------|------|------|
| UI 层 | 原始输入 → 抽象值 | 支持 zIndex 冲突裁决，允许多源并发 |
| Operation 层 | 抽象控制语义 | 不感知输入源与输出设备 |
| Mapping 层 | 抽象语义 → 设备输出 | 唯一产生设备输出的层 |

### 3.3 Node.js Server 模块划分

| 模块 | 职责 | 输入 | 输出 |
|------|------|------|------|
| WsClient | WebSocket 连接与消息收发 | WebSocket 消息 | ControlResultState |
| StateStore | 当前目标状态与序列 | ControlResultState | desiredState |
| Validator | 状态校验 | ControlResultState | 校验结果 |
| ApplyScheduler | 固定频率应用调度 | desiredState | 应用触发 |
| KeyboardExecutor | 键盘输入执行 | KeyboardState | KeyDown/KeyUp |
| GamepadExecutor | 手柄输入执行 | GamepadState | Xbox 状态 |
| SafetyController | 清零与异常兜底 | 异常信号 | 清零指令 |
| Metrics | RTT、异常、清零统计 | 运行数据 | 可观测性指标 |

### 3.4 职责边界冻结

#### Server 执行端必须负责

- 接收前端发送的控制状态快照
- 校验控制状态合法性
- 将控制状态映射为虚拟键盘和虚拟手柄输入
- 维持"状态驱动"的持续输入语义
- 在异常、断连、超时情况下独立清零
- 返回 ACK 用于 RTT 与延迟观测

#### Server 执行端不得负责

- 不得理解 UI/Operation/Mapping 语义
- 不得修改控制状态内容
- 不得合并多个控制来源（当前阶段单来源）
- 不得引入脚本、DSL 或不可验证逻辑
- 不得决定控制是否启用（仅执行状态）

## 4. 核心设计原则

### 4.1 状态驱动执行模型

系统的核心不变量：

1. **新状态覆盖旧状态**：任意时刻的控制可被描述为"当前状态"
2. **任意时刻可回到零输出**：控制中断后状态可被明确清空
3. **异常后不得残留输入**：不依赖历史事件顺序形成隐式状态
4. **控制行为不依赖前端 UI 是否存在**

执行语义：

> ControlResultState 表示：
> **"从现在开始，系统应当处于该输入状态，直到被覆盖或清零。"**

### 4.2 接收与应用解耦

- **WebSocket 接收线程**：仅更新 `desiredState`
- **ApplyScheduler**：周期性读取 `desiredState`，执行输入映射，不阻塞网络线程

时间权威：

> ApplyScheduler 是执行端唯一时间权威。
> 所有判断必须基于 ApplyScheduler 的时间基准：
> - 状态应用节奏
> - 超时清零
> - 心跳失效

应用频率：

- 执行端必须以**固定频率**应用状态
- 推荐频率：**125Hz**（对齐需求文档）
- 不得仅在"状态变化时"应用

### 4.3 安全回退优先

核心不变量：

> 任何异常、回退或禁用后的最终状态：
> **必须等价于"没有任何控制输出"。**

清零触发条件：

- WebSocket 断连
- 心跳超时
- 状态校验失败
- 执行层异常
- 显式零状态

清零特性：

- **立即、同步、不可延迟**
- **SafetyController 是唯一允许触发清零的模块**

超时清零参数：

- 默认超时阈值：**500ms**
- 时间起点：最后一次成功接收并校验通过的 ControlResultState

### 4.4 zIndex 冲突裁决机制

为保证在任何合法或非法配置下系统行为均可预测、可解释，在各层统一引入 `zIndex` 机制。

全局规则：

1. `zIndex` 为整数，默认值为 `0`
2. 数值越大，优先级越高
3. 不同 zIndex：高 zIndex 覆盖低 zIndex
4. 相同 zIndex：结果叠加

层级使用场景：

| 层级 | zIndex 使用场景 | 设计声明 |
|------|----------------|----------|
| UI 层 | **核心且推荐使用** | 允许多源并发输入 |
| Operation 层 | **防御性机制** | 不推荐使用，仅保证确定性 |
| Mapping 层 | **最终兜底** | 仅用于冻结冲突行为 |

### 4.5 模块边界约束

DeviceAdapter（Keyboard/Gamepad）约束：

- 不得保存跨帧状态
- 不得引入时间逻辑
- 不得决定清零

SafetyController 约束：

- 唯一允许触发清零的模块
- 清零优先级高于任何输入或布局执行

## 6. 子系统概览

### 6.1 Server（执行端）

#### 6.1.1 角色定义

执行端在系统中的角色是：

> **控制结果执行器（Control Result Executor）**

其职责是：

> 将前端生成的 ControlResultState（控制状态快照）
> 映射为宿主操作系统可见的输入设备状态。

#### 6.1.2 输入契约

- WebSocket 接收 ControlResultState
- ControlResultState 为完整状态快照
- 缺失 KeyboardState / GamepadState 等价于零状态

#### 6.1.3 输出契约

- 输出为宿主系统可见的：
  - 键盘输入
  - Xbox 360 控制器（XInput）输入
- 输出语义为状态维持，不是事件播放

#### 6.1.4 完整 Xbox 通道定义

执行端支持并仅支持以下 Xbox 360 控制器通道集合：

**摇杆轴（Axes）**

| 逻辑名 | XInput 通道 | 范围 |
|--------|-------------|------|
| LX | Left Stick X | [-1.0, 1.0] |
| LY | Left Stick Y | [-1.0, 1.0] |
| RX | Right Stick X | [-1.0, 1.0] |
| RY | Right Stick Y | [-1.0, 1.0] |

**扳机（Triggers）**

| 逻辑名 | XInput 通道 | 范围 |
|--------|-------------|------|
| LT | Left Trigger | [0.0, 1.0] |
| RT | Right Trigger | [0.0, 1.0] |

**按钮（Buttons）**

| 逻辑名 | XInput 按钮 |
|--------|-------------|
| A | A |
| B | B |
| X | X |
| Y | Y |
| LB | Left Bumper |
| RB | Right Bumper |
| BACK | Back |
| START | Start |
| LS | Left Stick Press |
| RS | Right Stick Press |
| DPAD_UP | D-Pad Up |
| DPAD_DOWN | D-Pad Down |
| DPAD_LEFT | D-Pad Left |
| DPAD_RIGHT | D-Pad Right |

#### 6.1.5 键盘方案说明

当前阶段（Executor v1.x）：

- 仅采用**用户态键盘输入注入方案**
- **不引入虚拟 HID 键盘驱动**
- **不实现内核态键盘设备**

能力边界声明：

- 不保证所有游戏在 Raw Input / 反作弊环境下接受该输入
- 若目标程序拒绝：视为系统外部约束，不构成执行端缺陷

### 6.2 Android Client（前端）

#### 6.2.1 角色定义

前端在系统中的角色是：

> **控制状态生成器（Control State Generator）**

其职责是：

> 将用户原始输入（触控、陀螺仪）
> 通过三层布局结构转换为 ControlResultState。

#### 6.2.2 前端必须负责

- 原始输入采集（触控、陀螺仪）
- 输入 → 抽象操作 → 设备输出的完整处理链
- 布局文件加载、校验、执行
- 控制结果生成（键盘 / 手柄）
- 状态 / 事件发送策略
- 延迟、丢包、连接状态的可观测性
- 安全清零与异常回退

#### 6.2.3 前端不负责

- 输入注入（由执行端完成）
- 游戏焦点判断
- 执行端超时清零实现（仅配置与观测）
- 任意脚本或用户代码执行

#### 6.2.4 UI 与系统节点分离设计

设计原则：

> **UI 组件 ≠ 系统节点**

- UI 组件只负责：呈现、命中测试、报告交互
- 系统节点存在于逻辑层，与 UI 解耦
- 系统节点可测试、可序列化、可回放

架构判断标准：

> 如果把 UI 全部换成另一套（甚至无 UI），
> LayoutEngine 和 Operation 是否还能工作？

#### 6.2.5 静态处理器模型

前端系统不支持用户脚本，而是基于：

> **少量、静态、可组合、参数化的处理器**

处理器能力边界：

- 纯函数语义
- 无副作用
- 无隐式状态
- 可预测输出

处理器分类：

| 类别 | 示例 |
|------|------|
| 输入处理 | deadzone / normalize |
| 语义处理 | curve / sensitivity |
| 输出处理 | axis → axis / axis → pwm |

## 7. 通信层概述

### 7.1 通信协议

| 项目 | 说明 |
|------|------|
| 协议 | WebSocket |
| 传输内容 | ControlResultState（完整状态快照） |
| 传输频率 | 推荐 125Hz |
| 连接方式 | localhost（本地连接） |
| 网络依赖 | 不依赖外部网络 |

### 7.2 ACK 与 RTT 协作

ACK 语义：

> ACK 表示：
> 执行端已将某一状态快照成功应用到虚拟设备层。

ACK 不表示：

- 游戏已响应
- 输入已被游戏处理

RTT 计算关系：

- RTT 由前端计算
- 执行端只保证 ACK 的一致性与序列正确性

### 7.3 通信异常处理

通信异常时：

- 立即触发清零
- 不依赖 ACK 才更新本地状态
- ACK 仅用于可观测性与诊断

## 8. 安全与稳定性设计

### 8.1 安全不变量

核心原则：

1. **不确定状态优先零输出**
2. **布局非法不得执行**
3. **任何异常不得残留控制**
4. **所有行为必须可解释**

### 8.2 清零策略

清零触发条件：

| 条件 | 说明 |
|------|------|
| WebSocket 断连 | 网络层异常 |
| 心跳超时 | 连接状态异常 |
| 状态校验失败 | 数据层异常 |
| 执行层异常 | 设备层异常 |
| 显式零状态 | 用户禁用 |

清零行为：

| 设备 | 清零行为 |
|------|----------|
| 键盘 | 遍历所有已按下按键，逐一发送 KeyUp |
| 手柄 | 所有按钮释放、所有轴归零、所有扳机归零 |

### 8.3 校验与容错策略

必须校验内容：

- 消息类型与版本
- 序列号单调性
- 键盘按键合法性
- 手柄轴 / 扳机范围合法性

非法状态处理：

| 类型 | 处理方式 |
|------|----------|
| 数值越界 | clamp |
| 未识别按键 / 按钮 | 丢弃并记录 |
| 结构非法 | 立即清零 |

### 8.4 可观测性

Server 执行端暴露：

| 指标 | 说明 |
|------|------|
| 当前连接状态 | WebSocket 连接状态 |
| 最后状态接收时间 | 时间戳 |
| 当前应用序列号 | 状态序列 |
| RTT | 延迟观测 |
| 超时清零次数 | 安全统计 |
| 异常清零次数 | 异常统计 |

Android Client 前端暴露：

| 指标 | 说明 |
|------|------|
| 控制状态 | 启用 / 禁用 |
| 布局状态 | 当前布局 |
| RTT | 延迟 |
| 丢包率 | 状态覆盖率 |
| 安全状态 | 是否中断 |

## 10. 当前阶段结论

### 10.1 系统定位

ControlX 在当前阶段被明确定位为：

- **单安卓设备本地控制系统**
- **状态驱动执行模型**
- **完整 Xbox（XInput）手柄支持**
- **键盘为阶段性用户态注入**
- **安全回退优先于输入完整性**

### 10.2 系统能力总结

| 能力 | 状态 |
|------|------|
| 触控输入采集 | ✅ 支持 |
| 陀螺仪输入采集 | ✅ 支持 |
| 键盘控制结果 | ✅ 支持（阶段性） |
| 手柄控制结果 | ✅ 支持（最终方案） |
| 布局编辑能力 | ✅ 核心能力 |
| 多布局管理 | ✅ 支持 |
| 安全清零 | ✅ 冻结 |
| 可观测性 | ✅ 支持 |

### 10.3 非当前阶段内容

以下内容不属于当前阶段范围：

- 跨设备远程控制
- 云端执行环境
- 多实例并行控制
- 控制结果录制与回放
